# AGENTS.md

## 项目定位

本目录是家政服务平台 Web 前端，使用 React + Umi 4 + TypeScript + Ant Design，调用同级项目 `home_service_backend` 提供的 REST API。当前前端只围绕三类智能体能力构建：检索推荐、对话式业务办理/表单补全、知识问答（RAG）。不要把前端扩展为任意自动化平台，也不要在前端实现后端业务规则、价格计算或权限判定。

优先级依次为：用户安全、权限边界、真实后端状态、可用性、可维护性、视觉一致性。所有界面都应能在网络异常、会话过期、权限不足和接口返回业务错误时给出可理解的反馈。

## 技术栈基线

| 技术 | 基线 |
| --- | --- |
| React | 由 Umi 4 管理的 React 18 类型与运行时 |
| Umi | 4.7.x，约定式路由、运行时配置、`@umijs/max` 能力按实际依赖使用 |
| TypeScript | 5.x，开启严格类型检查，禁止用 `any` 掩盖接口不一致 |
| UI | Ant Design 5；表格、表单、Drawer、Modal、Upload、Pagination 优先复用官方组件 |
| 包管理 | pnpm；锁文件为 `pnpm-lock.yaml`，不得混用 npm/yarn 安装依赖 |
| 样式 | Less/CSS Modules 或组件内样式；全局样式只放 `src/global.less` |
| 后端 | Spring Boot REST API，Session + Redis，Cookie 会话，不在前端保存 JWT |

版本以 `package.json`、`pnpm-lock.yaml` 和 `.umirc.ts` 为准。新增依赖前检查现有依赖和 Umi 兼容性，优先使用 Ant Design、Umi 官方能力；禁止提交未锁定的浮动依赖、密钥或第三方统计脚本。

## 当前代码布局

源码根为 `src/`，目录职责保持单向依赖：

```text
assets/       静态图片、图标及本地资源
components/   跨页面可复用展示组件（不承载页面业务流程）
config/       Umi/runtime 配置、请求和菜单配置
constants/    路由、角色、状态、组件类型等稳定常量
hooks/        可复用 React Hooks（会话、分页、权限、Drawer 等）
layouts/      根布局、后台布局、用户端布局、导航和全局错误边界
models/       Umi model 或领域状态（仅共享状态，不替代服务层）
pages/        路由页面，按业务域分目录
services/     后端 API 客户端，按 auth/user/shop/appointment/order/rag/agent 拆分
utils/        无状态工具：请求序列化、日期、金额、脱敏、错误映射
access.ts     Umi 权限能力计算，只从当前用户快照计算 UI 可见性
app.tsx       Umi 运行时配置、Provider、全局初始化
requestConfig.ts 统一请求拦截、错误处理、CSRF 和会话失效处理
```

页面目录建议：

```text
pages/
  auth/                 登录、注册、CSRF 初始化
  home/                 用户首页、服务分类、附近推荐
  shops/                商家列表、商家详情、预约入口
  appointments/         用户/商家/平台预约视图
  orders/               订单列表、详情、支付和确认
  merchant/             入驻申请、商家资料和服务项目
  admin/                后台统计、用户、商家审批、RAG、AI 日志
  agent/                对话 Drawer/Panel、消息和固定表单组件
```

Request/Response 类型与 API 客户端同域存放，例如 `services/shop/shopService.ts` 与 `services/shop/shopTypes.ts`。不要把 Entity、密码、Session 内容或后端内部错误对象映射到页面状态。

## 目录与依赖规则

- 页面只负责组合组件、读取路由参数和调用 service/hook；不得直接 `fetch`、访问 localStorage 中的认证信息或拼接 API URL。
- `services` 只负责 HTTP 请求、参数序列化和响应类型；不得渲染 React、弹 Toast 或修改全局 UI 状态。
- `components` 必须通过 props 接收数据和回调，不直接依赖具体页面；领域专用组件可放在对应页面目录下。
- `models` 只保存 UI 所需的短期状态；后端业务事实必须在接口成功后刷新，不能把模型推断当事实。
- `constants` 放角色、权限、状态、路径和组件类型，禁止散落魔法字符串。
- `utils` 必须无状态、可测试；业务规则放后端，不创建万能 `utils`。
- 共用 View 类型使用明确的 `*View`/`*Response`，输入使用 `*Request`；不要把 Request 和 View 放在同一对象中。
- 路由、菜单和权限表达式保持可搜索、可审计；移动文件时同步更新 import、路由和测试。

## 视觉与交互基线

整体风格为简约、留白充足、浅色低饱和配色。默认使用 Ant Design token，避免页面自行定义大量颜色。建议：背景 `#f5f7fa`，卡片白色，主色使用柔和蓝/青，危险操作使用 Ant Design danger 色；文本对比度必须满足可读性。

用户端首页：顶部为服务分类横向滚动栏，点击一级分类展开二级列表；主体展示附近推荐商家卡片，卡片至少包含商家图片、名称、标签、主要服务和距离/城市；点击进入商家详情。详情页顶部为图片 Carousel，下面展示可预约服务、价格单位、服务说明、营业状态和预约按钮。

用户端右侧提供智能体按钮，打开可调整宽度的 Drawer/Panel，不遮挡关键提交按钮。面板应保留当前对话展示、加载状态、重试入口和关闭操作；移动端改为全屏或底部抽屉。页面顶部提供消息入口和未读数量，订单发布、预约状态变化等后端真实事件通过刷新或轮询展示，不在前端伪造推送。

后台采用独立布局：左侧固定导航，至少包含统计大屏、用户管理、商家/入驻审批、服务项目、预约与订单、RAG 知识库、AI 日志；右侧为面包屑、页面标题、筛选区、表格/卡片和分页。不同管理员角色只显示有权限的菜单，但后端 403 始终是最终裁决。

## 角色与权限

不得创建 `ADMIN`、`MERCHANT`、`WORKER` 等替代角色。角色编码必须与后端保持一致：

```text
username_super_admin  超级管理员
username_sec_admin    安全管理员
username_aud_admin    审计管理员
username_sys_admin    系统管理员
username_normal_user  普通用户
username_pla_user     平台用户（商家入驻审批通过后）
```

`access.ts` 只用于菜单、按钮和页面入口的可见性；不能仅依靠前端隐藏实现安全控制。所有写操作必须处理 401/403，并在重新登录后恢复用户原意图。管理员后台不应向普通用户暴露后台路由；普通用户和平台用户使用用户端布局，平台用户可进入自己的商家管理页面。

建议权限粒度使用后端返回的 permission code，而不是在组件中比较角色名称。敏感操作（锁定用户、审批入驻、删除知识文档、支付、取消订单）必须显示二次确认，明确对象、状态和不可逆影响。

## 会话、认证与请求

后端使用 Session + Redis，前端不保存 JWT、密码、密码哈希或完整 Session 内容。请求客户端必须携带 Cookie（同源或明确配置 `withCredentials`），登录成功后通过 `/api/auth/me` 获取认证主体和权限。

统一请求层负责：

1. 发送 JSON、分页、排序和幂等键；
2. 处理 CSRF：先访问 `/api/auth/csrf`，写请求携带 `X-XSRF-TOKEN`；
3. 将后端统一错误映射为用户可读提示，不展示堆栈、SQL、Token 或内部路径；
4. 收到 401 时清理内存中的用户状态并跳转登录页；
5. 收到 403 时保留当前页面并展示无权限提示；
6. 对网络超时提供有限重试按钮，不自动无限重试非幂等写操作。

登录、注册、退出和密码修改页面不得记录密码到日志、埋点、URL、Redux/Umi model 或浏览器持久化存储。退出登录后应清理缓存的用户、菜单和未读状态，并调用后端注销接口。

## API 对接约定

服务层按后端接口组织，默认前缀为 `/api`：

```text
auth       /auth/login、/register、/me、/logout、/csrf
users      /users、/users/me
shops      /shops、/service-categories/tree
merchant   /merchant/applications、商家资料和服务项目
appointments /appointments
orders     /orders
agent      /agent/chat
admin/rag  /admin/rag/documents
```

分页统一转换为页面使用的 `{items,total,page,size}`；后端字段名、枚举值和金额精度不得在 service 外随意重命名。金额使用字符串或 `number` 加格式化函数展示，禁止浮点计算金额。日期统一按后端约定的 UTC/ISO 值解析和展示，不能依赖浏览器非标准解析。

预约页面必须在提交前显示商家、服务、地址、联系人、联系电话和期望时间；提交使用幂等键，成功后立即调用详情接口核验真实预约编号和状态。订单支付仅展示后端返回的 Stripe 沙盒信息和状态，不在前端自行判断已支付。订单、预约、商家审批状态均由后端状态机驱动，前端只允许展示后端允许的动作。

## 智能体 UI 约定

智能体面板只负责消息展示、输入、固定组件渲染和提交回调。后端返回的 `componentType`、`schemaVersion` 和字段 Schema 必须经过白名单校验；前端只渲染预先编写的组件，例如商家筛选、预约表单、地址选择、订单确认，不执行模型返回的 HTML、JavaScript 或组件代码。

交互顺序：

```text
用户输入 → 显示处理中 → 展示回答/固定表单
→ 用户编辑并确认 → 调用普通业务 API
→ 查询真实结果 → 在对话中展示单号、状态、金额或预约信息
```

支付、取消、账户修改、入驻审批等敏感写操作必须二次确认。组件提交失败时复用普通页面的校验和错误展示，不由模型猜测“已完成”。知识问答显示来源标题、来源地址/版本和更新时间；无可靠来源时明确提示未知。推荐结果最多展示后端返回的有限数量，并标明实时事实来自结构化接口。

## 表单、上传与地图

所有表单使用 Ant Design `Form` + `Form.Item` 校验，前端校验只改善体验，后端校验仍是最终规则。提交按钮在请求期间禁用并显示 loading；失败后保留用户输入，不重复创建幂等写入。

商家入驻位置使用高德地图相关后端接口返回的标准化地址和坐标；前端不得自行信任用户输入坐标或把高德密钥写入浏览器代码。图片上传只提交后端/COS 允许的对象 Key 和元数据，限制 MIME、大小和数量，预览 URL 应为短期签名或后端安全 URL，不把 COS Secret 暴露给前端。

## 错误、加载和空状态

列表页面必须区分首次加载、刷新、空数据、权限不足、网络失败和服务端错误。表格筛选、分页和排序应可复现到 URL 查询参数，但 URL 不得包含密码、Token 或个人敏感信息。危险操作使用 `Modal.confirm`，成功后刷新相关列表和未读计数。

错误提示使用稳定的业务语义：参数错误、未登录、无权限、资源不存在、状态冲突、重复提交、外部依赖失败分别提示；不显示后端堆栈和供应商密钥。对于暂不支持的功能（评价、投诉、售后、优惠券、工作人员排班/聊天、自动派单、平台估价、退款自动化等）显示明确的“当前版本暂不支持”，不要渲染假入口。

## 测试与质量门槛

提交前至少运行：

```bash
pnpm install --frozen-lockfile
pnpm build
```

新增页面应补充组件或页面测试，重点覆盖：权限菜单、401/403、表单校验、重复提交、分页筛选、空状态、网络失败、订单状态按钮、智能体组件白名单和敏感操作确认。提交前检查 `git diff --check`，不要提交 `node_modules`、`.umi` 生成物、构建产物、密钥和本地配置。

## 禁止事项

1. 不在浏览器保存 JWT、密码、密码哈希、COS 密钥、模型 Key 或完整 Session。
2. 不把前端隐藏菜单当作权限校验，不相信 URL 中的 userId、shopId 或金额。
3. 不在页面直接调用 Repository、数据库、Milvus、LLM 或第三方管理 API。
4. 不把后端 Entity、完整用户隐私、Prompt、模型原文写入 localStorage、日志或埋点。
5. 不使用 `dangerouslySetInnerHTML` 渲染模型输出；Markdown 也必须经过安全渲染和链接白名单。
6. 不无限轮询、无限重试或在失败后自动重复支付、预约、取消和删除。
7. 不修改后端枚举含义，不创建与后端角色冲突的前端角色。
8. 不为暂不考虑能力提前创建页面、路由、菜单、接口或假数据。
9. 不为了视觉效果牺牲键盘可访问性、移动端布局和错误反馈。

## 交付报告

完成前端变更时说明：新增/修改的页面和 service、涉及的后端接口、权限边界、状态/幂等处理、测试命令及未能执行的环境原因。若后端接口缺失，应先记录缺口和影响，再与后端一起设计兼容的请求/响应契约，不在前端猜测接口。
